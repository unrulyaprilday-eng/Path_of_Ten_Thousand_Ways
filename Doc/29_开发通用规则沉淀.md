# 开发通用规则沉淀

> 本文档用于沉淀本轮开发中已经反复验证、以后大概率还会继续复用的通用规则。  
> 目标不是替代 `AGENTS.md`，而是把“这次已经想明白的事”及时写下来，减少后续重复思考。

## 1. 使用方式

- 如果规则已经上升到项目级长期协作约定，应同步更新 `AGENTS.md`。
- 如果规则更偏当前 DEMO、当前技术栈或当前开发阶段的经验结论，可先记录在本文档。
- 后续开发遇到新的通用规则时，优先追加到本文档，而不是只留在聊天记录里。

## 2. 当前已确认的通用规则

### 2.1 通用程序与脚本可沉淀为公共库

- 当一段程序、脚本、配置读取、生成逻辑或工具函数已经在两个以上位置重复，或明显会继续复用时，应优先抽成公共库 / 公共模块。
- 不要为了赶当前功能进度，一直复制近似代码，导致后续维护和扩展成本持续上升。
- 公共能力应优先放在结构清晰、命名稳定的位置，例如：
  - `UNITY/Assets/Scripts/Common/`
  - `UNITY/Assets/Scripts/Systems/`
  - 独立的配置工具或生成脚本目录

### 2.2 UI 先验证结构，再补正式图片

- 当前项目的 UI 开发目标默认向商业化产品标准靠拢。
- 核心要求是：
  - 简洁
  - 明了
  - 可读性强
  - 信息层级清晰
  - 状态表达明确

- 当正式 UI 图片资源未就绪时，可以先用色块、纯色面板、描边框体和简化占位资源完成布局与层级验证。
- 这一步的目标是先确认：
  - 布局是否顺手
  - 视觉层级是否清楚
  - 文字是否易读
  - 信息是否拥挤
  - 关键操作是否一眼可辨

- 在布局方案经过确认之前，不必急着生成正式图片资源。
- 在布局通过确认之后，再进入正式图片、切图、边框、装饰和立绘资源的生成与接入。

### 2.3 占位 UI 也要按正式标准验证

- “先用色块顶住”不等于“先随便摆一下”。
- 就算是占位 UI，也应尽量模拟正式产品中的：
  - 模块分区
  - 对比关系
  - 信息密度
  - 主次层级
  - 交互落点

- 否则后面即使换成正式图，也只是把问题更华丽地保留下来。

### 2.4 一个页面只做一件事

- 开局三页应严格分工：
  - `定根脚` 只定身份底色
  - `受信物` 只定启程故事线与启程信物
  - `首境` 只定第一段地图与节点倾向
- 不要把“为何出山”“带什么上路”“先去哪修”重新揉回同一张卡。
- 如果一个页面已经承担了选择动作，就不要再额外塞入另一层核心决策。
- 根脚决定启程线候选池，不直接锁定唯一信物。
- `受信物` 页内部也要分层：启程故事线决定地图路线库与早期成长路径，具体路线仍由后续节点选择决定。
- 启程信物承接故事线带出的启动信物库，具体信物负责 Build 起手倾向。
- 入首境采用“信物收窄候选池”：一个信物可指向 2-3 个有因果关系的大地图，玩家从中选择第一脚踏入哪里；不要定死唯一地图，也不要做成全地图自由副本菜单。
- 首境卡必须低信息密度，只放地图名、风险词和一句极短气质文案；信物效果、构筑标签、节点权重和掉落概率留给后续系统。
- `入首境` 页采用弱背景 + 竖向大图卡结构。背景只托氛围，不承担选择；2 选 1 和 3 选 1 都保持接近的单卡尺寸，居中排列，不随候选数量把卡片拉宽或压扁。
- 不要把启程故事线直接做成职业 / 流派按钮，也不要让信物脱离故事线变成全局物品池。
- `携行之物` 不再作为前台页面名，前台统一显示为 `启程信物` 或 `临行一物`。

### 2.4.1 产品内文案不用设计说明语气

- 设计文档可以写系统职责，例如“根脚负责身份底色”“启程线负责地图路线库”。
- 游戏 UI 上屏文案不能像产品经理给开发讲项目，不能直接写“最终道途”“Build 倾向”“页面职责”“系统层”等解释词。
- `定根脚` 的上屏文案应像命书、案台、签文或旁白，例如 `签落案前，先认此身来处。`
- 数值效果也要用游戏内标签承载，例如用 `此身余荫` 承接轻效果，而不是直接写成纯系统说明段落。

### 2.4.2 DEMO 先做完整纵切

- 当前 DEMO 先完整打磨 `世家旁支 -> 3 条启程线 -> 信物首境候选 -> 三层节点 -> 天劫化身`，其中旧矿地窟仍是 P0 优先打磨的大地图。
- 根脚入口仍要展示，但其他根脚可以显示为 `命数未显`、`待解锁` 或类似状态。
- 不要为了“系统看起来完整”提前平均铺开多个根脚和多个首境，导致每条线都浅。
- 后续新增根脚时，也按“一个根脚至少 2-3 条启程线、每条线有启程信物、至少一个合理首境去向”的结构扩展。

### 2.5 开局页不挂持续信息栏

- 开局选择页的主任务是做当前这一步选择，不是回顾整套 build。
- 在 `定根脚 / 受信物 / 入首境` 这些起手页中，应隐藏底部或侧边的常驻牌组、构筑、奖励摘要栏。
- 这类持续信息栏更适合放在正式战斗、路线、战后奖励等已经进入局内推进的页面。

### 2.6 路线页不要伪装成重选流派

- 地图中的 `择前路` 页，主文案应优先表达“接下来走哪段历练、会先经历什么节点、节奏更稳还是更险”。
- 即便路线内部确实带有风格倾向，也不要让页面看起来像在重复选择一次 `万剑 / 雷 / 血` 主流派。
- 风格信息可以降到次级标签，路线节奏和节点顺序才是页面主信息。


### 2.6.1 首境后先首战，再择前路

- 当前 DEMO 的首境页已经承担“我第一脚踏进哪里”的正式选择，不要在首境确认后立刻再给一个同等重量的路线三选一。
- 首境确认后应先进入 `入场首战`，用短斗法兑现首境选择，让玩家先感到自己真的踏入了这张大地图。
- 入场首战胜利后先给一次战后奖励，再打开第一次正式 `择前路`。此时玩家已有血量、牌组和第一项补强，路线选择更像肉鸽判断，而不是开局菜单考试。
- 第一次择前路优先表达稳 / 险 / 构筑等节点节奏，例如 `矿口余烬`、`塌井深处`、`旧账暗室`，不得回退成 `万剑 / 雷 / 血` 这样的流派按钮。

### 2.7 开卷页 UI 微规则

- `开卷` 是启动页的前台名。页面已经切到高留白浅水墨方向后，按钮不应继续沿用大面积暗黑底板。
- 首页主按钮优先使用浅宣纸 / 淡金题签底、墨色文字和克制描边；次级按钮可以弱化，但不能弱到像加载失败或不可读。
- 禁用状态必须和普通次级按钮明确区分，例如 `继续悟道` 无存档时显示 `尚未立道`，并降低文字透明度。
- 首页右下信息签只承担轻量运行信息，不做大面板，不堆构筑详情。
- 首页右上只放低频轻入口，例如图鉴、设置、退出，不放商城、活动、邮件等破坏 DEMO 气质的入口。
- 首页动效应低频、低透明度、低位移：云雾慢漂、雷光偶发、按钮微弱流光、标题轻呼吸即可，避免做成页游登录页。

### 2.8 生图请求禁止并发

- 生图任务必须串行执行。无论使用内部 `image_gen` / `imagegen`，还是备用 `imagegen2`，一次只能发起 1 张 / 1 个任务。
- 当前任务必须完成、目检并决定落库或废弃后，才能开始下一张图。
- 不使用并行工具、批量并发、多路命令或同时重试来生成多张图片。
- 如果接口出现 502、524、远端断开等问题，只在单任务串行前提下降低尺寸、降低质量或稍后重试。

### 2.9 imagegen2 调用避坑

- 用户明确要求“重新生图”“不要调用编辑接口”时，只能走 `generate`，不要改用 `edit`，也不要用本地修图、局部重绘、抠图或补画来伪装成重新生成。
- `imagegen2.py generate` 的精确输出路径参数是 `--out`；不要写成 `--output`。图片格式使用 `--output-format png/webp/jpeg` 单独指定。
- 显式 `--size` 必须满足接口约束：宽高都是 16 的倍数，最长边不超过 3840，长短边比例不超过 3:1，总像素数不少于 655,360 且不超过 8,294,400。
- 16:9 草图优先用 `--ratio 16:9 --clarity 1K`，对应 `1536x864`；如果要压低尺寸，`1024x640` 是当前可用的低像素 16:10 近似下限。
- 遇到 `Remote end closed connection without response`、`SSL: UNEXPECTED_EOF_WHILE_READING`、`HTTP 502/524` 等错误时，先按网络 / 远端服务不稳定处理，不要把问题误判为提示词一定写错。
- 如果同一请求在合法尺寸、低质量、短提示词下连续断连，应停止反复重试并向用户说明接口不可用；不要继续靠增加并发、换编辑口或隐式换模型碰运气。
- 非透明普通生成默认坚持当前模型；除非用户确认，不要把 `gpt-image-2` 悄悄降到 `gpt-image-1.5`。透明输出触发的模型切换按 skill 规则单独处理。

### 2.10 牌库驱动半实时斗法

- 当前战斗主结构是 `牌库驱动的半实时斗法`。
- 灵气持续增长，飞剑、敌人、法器和功法持续演算。
- 玩家用抽到的手牌低频介入，不采用固定分段回合。
- 卡牌必须保留牌库、抽牌、手牌、弃牌和洗牌，不得退化为固定技能栏。
- 法器与功法多数应自动触发或条件触发，少数主动入口需要冷却、充能或灵气消耗。
- 不保留旧式分段回合作为教学或慢速辅助；新手引导只能用高亮、短提示、读条和预警，不改变战斗结构。

### 2.11 Windows 沙盒与 PowerShell 避坑

- 如果命令返回 `windows sandbox failed`、`helper_unknown_error`、`apply deny-read ACLs` 等 ACL 类错误，不要连续换多种复杂写法反复试同一件事。
- 先判断这是不是必要操作：
  - 必要的只读定位、图片尺寸检查、`git diff`、构建验证，可以用同一条更简单的命令申请一次明确提权。
  - 非必要的漂亮行号、完整文件倾倒、重复截图，应直接跳过或缩小范围。
- 提权申请必须尽量窄：
  - 只为当前文件、当前命令、当前验证目的申请。
  - 不申请过宽的 `python`、整盘读写或破坏性命令规则。
  - 不把删除、重置、覆盖等风险操作混在提权命令里。
- 读取代码优先用 `rg -n` 定位，再用 `Get-Content -LiteralPath ... -Encoding UTF8 | Select-Object -Skip ... -First ...` 截取小段。
- 遇到临时目录、截图、生成图无法用图片查看工具读取时，优先把最终候选落到工作区，再用 `Get-ChildItem`、PIL 尺寸/亮度统计或 Unity 接入验证；不要为了看图反复消耗多轮工具调用。
- `apply_patch` 如果因为 Windows ACL 失败，不要多次重试同一补丁。可改用 PowerShell / here-string 做精确替换，但必须满足：
  - 先定位目标片段。
  - 替换脚本使用精确字符串或结构化正则，失败即退出，不做半截写入。
  - 写入后检查关键片段、`git diff --check`，必要时再跑 `dotnet build`。
  - 写文件后保证 UTF-8、无多余 BOM、文件末尾有换行，避免引入无意义 diff。
- 多行 Python 只用于批量图片处理、复杂结构替换或统计分析；优先通过 PowerShell here-string 管道执行。不要把多行 Python、中文路径、f-string 和大量转义塞进 `python -c`。
- 一旦某类命令失败原因已明确是 ACL / 沙盒，不要继续花 token 解释和试错；直接切到“必要命令 + 窄提权 + 明确验证”的路径。

### 2.12 商业化水墨 UI 判断规则

- 本项目的水墨方向不是“把画面压暗”，而是：
  - 高留白。
  - 淡墨与宣纸质感。
  - 清楚的轮廓和气口。
  - 器物化卷轴、题签、印泥、玉石、轻金属。
  - 点翠青、石青、淡金、微朱砂只做局部落点。
- UI 背景只负责托氛围，不负责承载选择信息。真正的选择单位应是卡片、节点、按钮或文本组件。
- 如果一个页面已经需要三层以上蒙版、暗带、洗色、雾层才能让信息勉强可读，说明底图不适合做 UI 背景，应优先换成低细节、低对比、中心留白的新图。
- 生 UI 背景时，提示词应明确要求：
  - 中央大留白。
  - 低细节、低对比。
  - 可承载卡片与文字。
  - 无角色、无可读文字、无 Logo、无 UI 面板、无卡框、无强窗格、无密集建筑、无忙乱道具、无横向黑带、无重暗角。
- 交互文字、按钮字、数值、状态说明必须由 Unity 文本渲染；不要让生图模型直接生成中文正文或按钮字。
- 页面信息密度要服务当前动作：
  - `定根脚` 看身份。
  - `受信物` 看启程信物与故事线。
  - `入首境` 看去哪里。
  - `择前路` 看接下来怎么走。
  - 战斗页看血量、灵气、手牌、敌方意图和演出反馈。
- 不该做：
  - 复杂背景上继续叠复杂卡片。
  - 靠大面积黑底、紫黑厚涂或蓝黑雾气制造“高级感”。
  - 把页面做成 MMO 页游活动入口或现代玻璃 UI。
  - 把设计说明、系统职责、Build 解释塞进游戏内文案。
  - 用一堆角标、红条、蓝框同时表达选中、推荐、共鸣、风险等状态。
- 应该做：
  - 一页一个主决策。
  - 背景安静，卡片清楚，按钮明确。
  - 图多字少，状态统一，留白足够。
  - 先让远看轮廓成立，再让近看细节成立。
  - 发现“越遮越脏”时果断换 UI 托底图，而不是继续加蒙版。

## 3. 当前建议的执行顺序

1. 先做结构和信息层级
2. 用色块 / 占位块验证可读性
3. 用户确认布局方向
4. 再生成正式图片资源
5. 对已重复出现的通用代码和脚本，及时回收进公共库
