# 开发验证规范

> 本文档定义代码、配置、资源和商业化 UI 改动的通用验收流程。当前 DEMO 的具体状态、截图入口和输出清单由 README 指向的当前设计/验证文档负责；本文不绑定某一轮固定截图数量。

## 1. 验证原则

- 先验证行为正确，再验证完整体验链，最后验证装饰和细节。
- 编译通过只证明代码可用，不能证明状态机、资源导入、Canvas 布局和商业化画面成立。
- 验收必须覆盖用户真实阅读与操作顺序，不能只截脱离上下文的组件或 Prefab。
- 测试覆盖随改动风险扩展：窄代码改动做 CompileCheck；状态、页面、资源和流程改动必须补真实 Unity 验证。
- 自动像素统计只能发现空白、灰屏、裁切和尺寸异常，不能替代逐图目检。

## 2. 验证分级

| 改动类型 | 最低验证 |
| --- | --- |
| 纯文档 | 语义一致性、旧引用扫描、Markdown 链接检查、`git diff --check` |
| 常规代码/配置 | CompileCheck 构建、流程烟测、`git diff --check` |
| 跨模块状态或存档 | 构建、烟测、确定性状态覆盖、兼容/恢复场景 |
| UI 结构、文本和交互 | 构建、烟测、真实状态机连续截图、双分辨率、逐图目检 |
| 图片/字体/Resources 接入 | UI 全套验证、Unity 重新导入、资源 key/回退、透明与交互检查 |
| 场景、Prefab、序列化或 Package 变更 | 使用项目锁定版本的 Unity Editor 实际导入/运行验证 |

## 3. 常规代码验收

从项目根目录执行：

```powershell
dotnet build UNITY\CompileCheck\CompileCheck.csproj
dotnet run --project UNITY\CompileCheck\CompileCheck.csproj
git diff --check
```

通过标准：

- CompileCheck 为 `0 警告 / 0 错误`。
- 烟测输出与当前 README/当前验证文档声明的成功标记一致；文档重构后不得继续用过期成功文案冒充当前流程通过。
- `git diff --check` 通过；仅项目既定的 CRLF 提示可以接受。
- 新增的核心机制、状态转换和数据契约有最小可验证入口，不只依赖人工点击。

## 4. 真实状态机截图

- 商业化流程截图工具必须沿运行时真实状态机推进，按用户实际阅读顺序捕获进入页、选择页、确认后页面和下一操作状态。
- 优先通过公开玩法接口推进。只有测试状态无法稳定到达时，才允许在 `Assets/Editor/` 工具中使用反射；必须显式校验前置状态，失败时抛出异常，不能静默继续。
- Editor 工具可以确定性结束测试战斗，但不得注入不存在的中盘节点、伪造奖励、绕过控制器直接生成结算，或用演示数据替代实际运行历史。
- 截图工具只属于 Editor 验证程序集，测试性状态推进不得进入正式运行时程序集。
- 相同的状态推进、等待布局和截图读回逻辑出现两次以上时，沉淀为共享 Editor 辅助方法。
- 当前应捕获哪些页面、状态和条件分支，以当前验证文档为准；不得把历史上的固定 3 张、11 张或 20 张清单当成永久标准。

## 5. Unity 同步截图

- 批处理截图统一使用临时 `ScreenSpaceCamera + RenderTexture + ReadPixels + File.WriteAllBytes` 同步读回。
- 不依赖 `ScreenCapture.CaptureScreenshot` 的异步落盘；无可见 GameView 时它可能只输出成功日志却不生成文件。
- 每次切换状态后等待足够帧数，让 `Start/Update`、LayoutGroup、CanvasScaler、动画初始状态和 Resources 加载完成。
- 截图完成前检查 Canvas 尺寸、目标宽高比和关键对象存在性；不稳定即失败，不写入“通过”文件。
- 截图写入项目根 `tmp/`，不复制到 `Assets/`，不作为正式资源提交。

## 6. Unity 运行约定

- 运行前读取 `UNITY/ProjectSettings/ProjectVersion.txt`，使用项目锁定版本的 Unity Editor。
- 不同时启动两个指向同一工程的 Unity Editor。命令外壳先返回时，先查询并等待 `Unity.exe` 子进程退出，再读取日志和截图，不得立刻重复启动。
- 如果交互式 Editor 正占用工程，优先等待释放。确需最小验证副本时，只复制验证必需的 `Assets`、`Packages` 和 `ProjectSettings`，明确记录副本路径和局限，不能把副本结果冒充原工程所有状态均已验证。
- 新增或修改 Editor 截图工具后，保留 Unity 生成的 `.meta`，并确认重新导入无脚本编译错误。

## 7. 分辨率与文件验收

- 商业化页面默认至少验证 `1920x1080` 与 `1280x720`。
- 两种分辨率保持同一阅读顺序、主操作层级和角色/敌人空间关系，不能只做等比缩小后让文字、节点、卡牌或按钮失去可读性。
- 固定格式组件应有稳定尺寸和响应式约束；动态候选数量不得改变卡片比例、主图比例、基线和关键间距。
- 截图文件必须真实存在，尺寸和 RGB/RGBA 模式正确；不能只凭日志中的 `Captured` 文案判定成功。
- Unity 日志不得出现脚本编译错误、未处理异常、空引用、非法状态、导入失败或截图流程中止。
- 可使用像素方差、区域覆盖率、缩放相关性和非空像素检查发现灰屏、只渲染顶部、布局未稳定或状态截图雷同，但这些数据只是辅助证据。

## 8. 逐图评审

每张截图按以下顺序检查：

1. 页面职责与阅读顺序。
2. 主选择、主行动或战斗对峙关系。
3. 状态、路径、敌方意图和动态文字可读性。
4. 场景连续性、角色比例与资源实际导入结果。
5. 动态反馈、材质和装饰。

通用拒收项：

- 页面仍像网页表单、报表或通用暗色卡集合。
- 多层嵌套面板、深色旧框、占位方块或高纹理小框重新出现。
- 文字溢出、遮挡按钮、卡片不同高、节点连线错位或候选数量导致布局跳变。
- 敌人主体缺失、角色悬空、攻击空间被 HUD 吞噬或锁定标记不可辨。
- 绿边、黑底、白边、矩形雾层、纹理污染和背景压住文字。
- 装饰层阻挡交互，锁定项仍表现为可行动，或截图状态与实际数据不一致。

只要存在拒收项，本轮目标仍未完成；不能因为构建成功、文件非空或像素统计达标就收口。

## 9. UI 结构与交互验收

- 页面只保留一个主承载层，摘要、路径和状态优先使用留白、无框信息带或细线分区。
- 战斗、地图、奖励、修炼、事件、整备和结算职责不同，不复用同一套“通用卡 + 点击领取”骨架。
- 场景图负责氛围与空间连续性；正文、按钮、状态和数值由 Unity 文本与交互组件表达。
- 动态长文使用稳定容器、换行和截断，不能覆盖下一段内容或操作区。
- 卡牌、路线和候选单位固定宽高、同一基线、稳定间距；至少验证最少和最多候选数量。
- 装饰、场景洗色、雾层、印记和连线统一关闭 `raycastTarget`；截图成立后仍要实际检查交互层。
- 战斗 UI 先验证空间构图与对峙关系，再检查核心操作、状态可读性、动态反馈和装饰材质。

## 10. 资源接入验收

- 资源同时存在于 `UNITY/Assets/Art/<Category>/` 与 `UNITY/Assets/Resources/Art/<Category>/`，同名内容一致且各自 `.meta` 正常。
- 实际 `Resources key` 与代码、配置和制作单一致；正式图失败时回退顺序可用，不出现空白或半成品。
- 透明资源检查真实 RGBA、四角透明、alpha bbox、安全边及亮/暗底合成；不得仅看缩略图。
- 角色、Boss、场景和 UI 必须放入实际运行容器复核主体比例、裁切、纵深、基线和文字承载，不能用 `preserveAspect` 掩盖错误构图。
- 装饰图层关闭交互，字体在未安装系统字体的构建环境中仍能显示完整中文、数字和标点。

## 11. 变更后的截图范围

- 单组件视觉修正至少重截该组件所在页面及其前后状态。
- 页面结构或状态跳转改动重截对应连续流程，不能只截单页。
- 共用 HUD、布局系统、资源加载器、状态机或跨页面材质改动，应重跑当前完整流程截图集。
- 涉及随机地图、不同候选数、多敌人、Boss 构图、隐藏条件或存档恢复时，补充确定性种子/测试档覆盖，不用一张标准路线截图代表所有分支。

## 12. 开发记录

每次结构级改版或资源接入记录：

- 拆掉的旧结构和最终替代结构。
- 状态、路线、奖励或交互语义变化。
- 复用/新增资源、精确版本、来源和加载 key。
- 失败、拒收原因、重试和降级方案。
- 自动截图范围、实际暴露的问题和修正结果。
- CompileCheck、烟测、Unity 日志扫描、逐图复核和 `git diff --check` 结果。

记录写入 `11_资源制作单与开发记录.md` 或当前功能专项记录；不能只留在对话和临时日志中。
