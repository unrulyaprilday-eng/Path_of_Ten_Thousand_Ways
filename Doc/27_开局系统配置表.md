# 开局系统配置表

> 本文档不再只承担“把 26 写成一篇策划表格”的职责，而是作为 Unity DEMO 配置化工作的设计锚点。  
> 对应的程序可读配置已落地到：
>
> - `UNITY/Assets/Data/CSV/`
> - `UNITY/Assets/Data/JSON/game_config.json`

## 1. 本文档现在管什么

本篇仍然以 `26_开局结构与启程系统设计.md` 为第一来源，但不再局限于“开局展示表”。

当前配置拆分范围已经扩到两层：

1. 完整开局系统配置
   - 根脚
   - 传承道痕
   - 境域模板
   - 启程线
   - 节点偏向 / 奖励偏向
   - 显化阈值
   - 开局候选生成规则
2. 当前 DEMO 核心玩法配置
   - 卡牌
   - 起始牌组
   - 功法
   - 法器
   - 遗珍
   - 路线模板
   - 敌人与 Boss
   - 奖励优先级
   - 战斗常量

当前前台命名补充：

- UI 不再显示 `携行之物页`，统一显示为 `受信物页`。
- 旧字段 `carry_item_name` / `carry_item_effect` 继续作为程序兼容字段，前台解释为 `启程信物` / `信物效果`。
- 根脚决定启程线候选池，启程线绑定启程信物；不要从全游戏物品池单独抽信物。

这样处理的原因很直接：

- 如果只把 `27` 拆成“开局 CSV”，核心玩法仍然埋在代码里，配置化是不完整的。
- 当前 DEMO 已经进入“可玩闭环 + 持续调数值”的阶段，卡牌、功法、路线和 Boss 也必须进入同一套表结构。

## 3. 字段规则

统一约定：

- 主键统一使用 `snake_case`
- 百分比修正存裸值，例如 `12` 表示 `+12%`
- 布尔值统一使用 `true / false`
- 需要对接现有 Demo 代码枚举的位置，保留 `runtime_enum`
- 需要对接运行时卡牌 / 池子 / 路线 key 的位置，保留 `card_id` / `pool_id` / `route_plan_id`

建议分工：

- 策划优先编辑 `CSV`
- 程序优先读取 `JSON`
- 如果后续接入真正的数据加载器，源头仍建议以 `CSV` 为准

- 当前 DEMO 首版先完整开放 `世家旁支 -> 3 条启程线 -> 旧矿地窟`，其他根脚可以展示为未开放。

## 5. 为什么把 DEMO 运行数据也并入这套表

因为当前 DEMO 里以下内容仍然高度硬编码：

- `DemoCardLibrary`
- `DemoGongfaLibrary`
- `DemoArtifactLibrary`
- `DemoRelicLibrary`
- `DemoRewardService`
- `DemoArtifactRewardService`
- `DemoMapRoutePlan`
- `DemoGameController` 中的敌人生命和节点驱动参数

如果只配置化开局入口，会出现一个很别扭的局面：

- 开局是表
- 中盘奖励是代码
- 路线是代码
- Boss 参数也是代码

这不利于后续做：

- 数值调优
- 批量内容扩充
- 流派增补
- 节点模板扩充
- 掉落权重联调

所以本轮已经顺手把当前 DEMO 的核心运行数据一并抽表。

## 7. 下一步建议

建议按以下顺序继续推进：

1. 把开局入口真正切到根脚 / 启程线 / 启程信物 / 首境模板配置
2. 先完成 `世家旁支 -> 旧矿地窟` 的完整纵切，再扩其他根脚
3. 继续把 `DemoBattleState` 中剩余高频硬编码数值迁到配置，尤其是半实时灵气增长、抽牌间隔、冷却与敌人意图读条
4. 增加配置校验，防止缺字段或错 key 时静默回退
5. 视需要补一个编辑器内重载入口，减少改表后的手动重进 Play 成本

## 8. 当前取舍说明

本轮优先目标是：

- 把文档里的 `27` 变成真正程序可读配置
- 而且不局限于开局，直接覆盖当前 DEMO 核心闭环

因此本轮先完成了：

- CSV 主表落地
